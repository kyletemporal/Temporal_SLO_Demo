# Worker tuning load test (k6, gRPC straight to Temporal)

A stepped, open-model load test that starts Workflows **directly over gRPC**.
There's no application or HTTP shim in the path, so the same script runs
against Temporal Cloud (API key or mTLS), a self-hosted cluster, or a dev
server. It's built for one question: **did that tuning change move the Worker's
capacity?**

Everything you need is in this folder:

| File | What it is |
|---|---|
| `worker-tuning.js` | The test |
| `temporal-api.protoset` | The Temporal WorkflowService descriptors k6 loads. Generated by `go run ./tools/k6protoset` from `go.temporal.io/api` v1.63.4 |
| `uuid.js` | Request-id generator, inlined so the test runs without internet access |

It needs **k6 v0.55+** (built-in `k6/net/grpc` with `loadProtoset` and TLS).
There are no extensions and no `npm install`.

## Run it

```bash
# Self-hosted / dev server (plaintext)
TEMPORAL_ADDRESS=temporal.internal:7233 TEMPORAL_NAMESPACE=perf \
TASK_QUEUE=payments WORKFLOW_TYPE=PaymentWorkflow INPUT_JSON='{"amount":1}' \
k6 run worker-tuning.js

# Temporal Cloud, API key
TEMPORAL_ADDRESS=<region>.<cloud>.api.temporal.io:7233 TEMPORAL_NAMESPACE=<ns>.<acct> \
TEMPORAL_API_KEY=$KEY TASK_QUEUE=... WORKFLOW_TYPE=... k6 run worker-tuning.js

# Temporal Cloud, mTLS
TEMPORAL_ADDRESS=<ns>.<acct>.tmprl.cloud:7233 TEMPORAL_NAMESPACE=<ns>.<acct> \
TEMPORAL_TLS_CERT=client.pem TEMPORAL_TLS_KEY=client.key ... k6 run worker-tuning.js
```

In this repo, `make k6-tuning` runs it against the lab's Java Worker
(`lab-java`) and pushes k6's metrics into the stack's Prometheus, where the
**Workers — Tuning** board shows them.

| Variable | Default | Notes |
|---|---|---|
| `TEMPORAL_ADDRESS` | `localhost:7233` | host:port of the frontend |
| `TEMPORAL_NAMESPACE` | `lab` | Cloud: `<ns>.<account>` |
| `TASK_QUEUE` / `WORKFLOW_TYPE` | `lab-java` / `LabWorkflow` | Your Worker must be polling this queue and registered for this type |
| `INPUT_JSON` | lab input | One JSON argument, sent as `json/plain`. It must deserialize into your Workflow's parameter |
| `STEPS` | `2,120 4,120 8,120 16,120` | `rate,holdSeconds` pairs; the rate is starts/s |
| `RAMP_S` | `20` | Ramp between steps |
| `WORKFLOW_EXECUTION_TIMEOUT` | `15m` | Leftovers end themselves. Set it above real duration + worst backlog |
| `WORKFLOW_ID_PREFIX` / `RUN_ID` | `k6-tuning` / generated | IDs are `<prefix>-<run>-<vu>-<iter>` |
| `TEMPORAL_API_KEY` | | Sends `authorization` **and** `temporal-namespace` |
| `TEMPORAL_TLS_CERT` / `_KEY` / `_CA` | | mTLS. `TEMPORAL_TLS=true` forces TLS without credentials |
| `TEARDOWN_WAIT_S` | `10` | Pause before counting Workflows still running |

## How to tune with it

1. Pick **one** Worker setting to test. Run the test on the current config.
2. Change that one setting (flip the flag), wait for the swap, and run the test again.
3. For each step, read the Worker side, not k6: Activity and Workflow Task
   **schedule-to-start p95**, slots, and poll latency on the **Workers —
   Tuning** board, or your own.
4. **Capacity is the last step where schedule-to-start stays flat.** The change
   helped if that step moved up.
5. Read the teardown line: `N Workflows from this run still Running`. Any
   non-zero N is backlog the Workers never caught up on. Measured with one
   Activity slot at 4 starts/s for 20 s: **88 still running**.

## What k6 measures, and what it does NOT

k6 sees only `StartWorkflowExecution`: did the **server accept** the start, and
how fast. Starts stay fast while Workers fall arbitrarily far behind. **Worker
capacity is never in the k6 summary.** It's in the Workers' metrics and in
the teardown count.

The summary splits outcomes on purpose:

| Metric | Meaning | Action |
|---|---|---|
| `temporal_starts_ok` | accepted | |
| `temporal_starts_throttled` | `RESOURCE_EXHAUSTED`: a namespace RPS/APS limit (Cloud) or frontend rate limit (self-hosted) | **The step is invalid.** The load never reached the Workers. Raise the limit or lower the step |
| `temporal_starts_failed` | any other gRPC error, tagged with `code` | Usually auth, namespace, or a malformed input |
| `dropped_iterations` | k6 itself couldn't keep the rate | Add VUs or move k6 closer to the cluster |

All of these are thresholds, so a run that didn't deliver its load **fails**
instead of producing numbers that look like results.

## Landmines

- **Closed-model load hides backlog.** VUs that wait for each Workflow slow down
  to match the Workers, so a backlog never forms. This test uses
  `ramping-arrival-rate`, which starts at the rate you set regardless.
- **Hold each step long enough.** Several Workflow durations, plus two
  Prometheus scrape intervals. A 30 s step on a 60 s Workflow measures the ramp,
  not capacity.
- **Change one thing at a time.** Two settings changed together can cancel out
  or mask each other.
- **Unique IDs per run.** A reused Workflow ID is rejected or deduplicated by
  the server: load you think you sent but never ran. IDs include a per-run
  id. **Measured bug, now fixed:** the first version made that id in k6's init
  code, which runs **once per VU**, so 4 VUs used 4 ids. The teardown then
  counted 0 of 88 Workflows still running, and the printed cleanup command
  would have missed them all. The id now comes from `setup()`.
- **`requestId` must be unique per start.** The server deduplicates retried
  starts by it.
- **API keys need `temporal-namespace`.** A raw gRPC client (k6, grpcurl) gets
  `PERMISSION_DENIED: Request unauthorized` without it, even with a valid key.
  The script sends it.
- **Cleanup.** `setup()` prints the exact terminate command for this run. The
  default 15 min execution timeout ends leftovers anyway. Don't point the test
  at a namespace whose SLO dashboards you care about.
- **The teardown count needs advanced visibility** (`STARTS_WITH`): SQL
  visibility on 1.20+, Elasticsearch, or Cloud. If the call fails, the error is
  printed, not hidden.
- **Run k6 near the cluster.** Start latency includes the network. It doesn't
  change Worker capacity, but a slow link plus too few VUs shows up as
  `dropped_iterations`.
- **Push k6 metrics next to the Worker metrics** (`-o experimental-prometheus-rw`,
  `K6_PROMETHEUS_RW_SERVER_URL`), so step boundaries and Worker latency share a
  time axis. The counters for throttled and failed starts only exist after the
  first event; the dashboard handles that.
