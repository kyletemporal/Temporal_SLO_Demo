# Worker scale benchmark

- Offered load: **80/s** for **2m** per step (last **60s** measured)
- Activity delay: **50ms** — one activity slot sustains ~20 activities/sec

Laptop numbers from a single-container Temporal running all four roles beside the load generator and the whole observability stack. **Read where the curve bends, not the absolute values.**

## Reading it

**Throughput did NOT scale** — 73.8/s → 70.1/s across the sweep. Added Workers bought little or nothing, which means the bottleneck is not fleet size. Check, in order: per-Worker concurrency (`MAX_CONCURRENT_ACTIVITIES`), then the Temporal server, then the load generator itself. **An autoscaler would make this worse** — more Workers polling a server that is already the constraint adds poll load without adding capacity (that is scenario 8, poller flood).

**Schedule-to-start ROSE from 0.203s to 0.290s** as Workers were added. Queue wait getting worse with a bigger fleet means the added Workers are contending for something rather than draining the queue — the constraint is downstream of the fleet (server, persistence, or the load generator). An HPA scaling on this signal would scale UP in response, make it worse, and scale up again.

### What each column tells you

| Column | Reads as |
|---|---|
| Throughput below offered | The fleet cannot keep up. The gap is backlog being built. |
| S2S p95 rising | Tasks are waiting for a poller. The first symptom of saturation. |
| Min slots free at 0 | Slot-bound. More Workers will not help; raise concurrency. |
| Min slots free high, S2S high | Worker-bound or server-bound, NOT slot-bound. |
| Sync match falling | The queue stopped draining instantly — tasks now round-trip persistence. |
| Poll success falling | More pollers than work. Over-provisioned (see scenario 8). |
| Efficiency below ~0.8 | Diminishing returns. Near the knee of the curve. |
